# Storyboard público en el board YOD

Dirección solicita el19-oct-2026 conservar GitHub Pages, PorteroGoogle y el circuito de Sala; no crear Sites ni bases independientes para presentaciones. Esta corrección de plataforma no autoriza producir una presentación final antes de revisar su storyboard.

## Flujo y fuente

PDF autorizado → guion editorial versionado → storyboard público del board → corrección privada CHN → PRODUCCION de Sala → revisor vigente → cambio por PR → comprobación de Pages.

El registro original del proyecto y sus hojas conservan la fuente operativa. Un storyboard preliminar basado en un documento identificado es un snapshot editorial; no sustituye celdas vivas ni autoriza modificar cifras financieras. Las solicitudes de cambio de guion se envían como revisiones a Sala; no se simula que un override local modificó el modelo.

## Contratos reutilizados

CTR-PRESENTATION-PINS-INGEST: yodChinche local, sobre privado, captura acotada, ID/huella, comprobación de recepción, sin duplicar POST ambiguo. No nuevo Sheet, backend, baseD1 ni cron.

Acceso explícito Master Developer con Portero vigente en el mismo origen GitHub. Entrada pública sin gate automático; sesión sólo para revisión. Validar rol mediante canje del servidor y no confiar en pyod_rol cacheado. La autorización final de escritura sigue en Sala. El borrador público no se vuelve privado por ocultar un botón; no publicar comentarios, capturas ni credenciales en el bundle. No se modifican ACL ni el servicio de identidad.

## Alcance y pruebas

Primera etapa: storyboard, guion publicado por instrucción de Dirección, captura y entrega al circuito existente. Sin conducción sincronizada ni ofertas activas hasta su etapa autorizada. Preservar slider, rotor acotado, iPhone vertical/horizontal y reversa.

Pruebas sintéticas: visitante sin sesión, canje válido/rechazado/tardío, cambio de identidad, captura y cancelar, envío/acuse, offline y respuesta ambigua. Cero escrituras de negocio de prueba. Publicación pública del código exacto y acuse real de Dirección se registran separadamente.

Rollback: revertir consumidor frontend por PR; preservar IDs, IndexedDB y sobres de Sala. No borrar versiones anteriores ni datos del proyecto. Retirar Sites como destino del registro activo; conservar temporalmente evidencia para reconciliar revisiones si existieran.
