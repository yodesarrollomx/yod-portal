# YOD Core 10X · bitácora técnica del PR281

## Alcance de esta entrega

Contrato de trabajo reforzado, almacén SQLite transaccional y CLI local probados.
La integración productiva con transportes autenticados, el motor existente del
Despacho y los procesos comerciales **no está activada**. Código publicado no
significa que la empresa opere automáticamente ni acredita una mejora 10X.

El Buzón no se utiliza mientras Claude no esté disponible. Esta es la bitácora
**técnica auxiliar** del cambio; no se afirma haber actualizado el registro
operativo de Drive ni haber recibido un acuse de Claude.

## Historial de ejecución

**17-oct-2026, primera entrega.** Se revisó el portal, catálogo, instrucciones de
arquitectura y coordinador de carga existente. Se crearon la rama
`codex/yod-core-fundacion-20261017`, un contrato aislado y cuatro pruebas; PR281
quedó en borrador. No había integración ni persistencia. El fallo de selección
de workspace de Render no autorizaba elegir uno arbitrario.

**18-oct-2026 UTC / 17-oct Hermosillo, continuación solicitada: «termina».**
Se leyó el estado real del PR: las pruebas Node, portal y obra habían pasado,
pero la corrida de Arquitectura falló en el registro de impacto. Se añadió CI
Core con permisos de lectura y un artefacto reproducible del código público.
La descarga directa de Git no funcionó; el artefacto de GitHub permitió ejecutar
las verificaciones en el entorno local, sin credenciales ni documentos privados.

Se corrigieron dos vacíos del boceto: ausencia de responsable obligatorio y
reanudación de una escritura incierta sin conciliación. La revisión independiente
queda ligada al artefacto y revisión exactos. El ledger no acepta un simple
`passed:true`: requiere el adaptador de verificación de confianza; sin él falla
cerrado. La conciliación de escrituras exige otra guarda independiente.

Se implementaron transacciones tarea/evento/recibo, índice único activo,
request_id idempotente, revisión optimista, dependencias, checkpoints y consultas
de estados. Se probaron reinicio, dos procesos competidores, caída antes de
commit y rollback cuando falla el recibo. No se llamaron endpoints de negocio.

**Resultados locales:** 36/36 pruebas específicas de Core aprobadas; la suite del
portal pasó 847/847 (incluye 16 de esas 36). Atlas, OS, portal y obra aprobados.
La comparación externa de accesos no pudo descargar su referencia desde el
contenedor; se exige su comprobación en GitHub Actions, no se omite.

**Comprobación remota, 18-oct-2026 06:16 UTC.** La corrida de registro
[39103428710](https://github.com/yodesarrollomx/yod-portal/actions/runs/39103428710)
terminó correctamente: regeneración del modelo/vistas, suite combinada, OS,
portal, comparación externa de accesos, obra e impacto. Guardó el registro
arquitectónico como `a112852e8e72f3474fa9357e022e820288ba32e7`, sobre el código
`003a25ccea3e227766d6edb9f8c962662f99b7fb`. No se omitió ninguna comprobación.
La integración del PR se condiciona a las verificaciones obligatorias sobre
su commit final; el resultado de integración y los acuses de publicación se
consultan en [PR281](https://github.com/yodesarrollomx/yod-portal/pull/281).

Se contrastó la arquitectura con el motor privado existente: ya dispone de metas,
cola y registros durables. Este trabajo no los reemplaza ni reactiva metas
paradas. No se crea otro servicio, no se cambian URLs, ACL ni secretos, y no se
contratan recursos. La capacidad comprobada es la del paquete local; no del
conjunto de integraciones de la empresa.

## Registro e impacto

Propuesta `CHG-YOD-CORE-20261017`, componente `SYS-YOD-OS`. El registro y las vistas
se generan de forma determinista; si otro agente cambia la revisión del modelo,

de este PR, nunca main, y exige pruebas antes de guardar. No sustituye las
comprobaciones obligatorias ni la integración mediante PR.
